# OpenEmpiric v1.0.2

## Release Overview

OpenEmpiric v1.0.2 introduces a series of modularization, path resolution improvements, and decoupling of preflight actions to establish a highly maintainable, clean monorepo architecture. 

## What Changed and Why

### 1. Preflight and Bootstrap Decoupling
- **Change**: Separated project initialization (`oem init`) from specific skill installation (such as the OpenCode skill). Skill installation is now explicitly invoked via `oem setup opencode`.
- **Why**: Decoupling prevents external/optional skills from interfering with core project bootstrapping and simplifies preflight checks, ensuring a clean and independent workspace preparation stage.

### 2. Monorepo Refactoring and Modularization
- **Change**: Extracted active project binding logic and error definitions from `server.py` into a dedicated [project.py](file:///home/xpajonx/.config/openempiric-dev/packages/oem-knowledge/src/oem_knowledge/project.py) module. 
- **Change**: Modularized the large, monolithic MCP tool definitions inside `server.py` into clean, logical submodules:
  - `tools/lifecycle.py`
  - `tools/concepts.py`
  - `tools/skills.py`
  - `tools/source.py`
  - `tools/diagnostics.py`
- **Why**: This drastically reduces code churn and simplifies maintenance of tool implementations. Circular dependency risks between CLI utilities and system runtime are neutralized by isolating CLI helper functions.

### 3. Packaging and Modern Resource Discovery
- **Change**: Canonicalized resource discovery to use modern `importlib.resources.files` instead of hardcoded paths. Deleted deprecated root directory footprints (`plugins/`).
- **Why**: Ensures reliable plugin resource packaging and makes the application fully compliant with modern Python packaging standards, verified via a automated test compiling and loading the wheel inside a clean virtual environment.

### 4. Consolidated Test Structure
- **Change**: Consolidated all tests under the package hierarchy inside `packages/oem-knowledge/tests/integration/` and `packages/oem-knowledge/tests/adapters/`.
- **Why**: Creates a clean separation between external interface adapter tests and end-to-end integration flows.
